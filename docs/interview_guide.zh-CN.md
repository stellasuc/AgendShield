# AgentShield 面试指南

[English](interview_guide.md)

## Q1. AgentShield 解决什么问题？

工具型 Agent 可以获取敏感数据，并产生邮件、记忆写入或响应发布等真实副作用。AgentShield 在受保护后端可达之前，把能力提案转换为经过策略校验、带状态且可审计的事务。它关注完整执行生命周期中的运行时强制控制，而不只是内容审核或 Prompt 过滤。

## Q2. 为什么仅做动作级校验不够？

相同的 `email.send` 在载荷为聚合统计时可能安全，在载荷为原始客户记录时则不安全。决策需要此前工具结果、目的、来源、转换、去向与授权等事实。AgentShield 将这些事实落到合规状态和血缘中，而不是要求每个孤立调用自行携带全部可信上下文。

## Q3. 项目与 SHIELDAGENT 有什么关系？

AgentShield 是受 SHIELDAGENT 策略驱动动作校验启发的独立工程项目。SHIELDAGENT 使用相关状态和交互历史校验当前动作；AgentShield 增加显式类型化状态、对象血缘、生命周期钩子、Broker 中介、持久化副作用、审批和重放控制。它不是官方实现，也不声称拥有 SHIELDAGENT 的训练模型、概率电路或基准结果。

## Q4. 为什么需要持久化 Compliance State？

安全事实经常早于需要使用它的动作出现。持久状态让后续外部传输复用此前轨迹产生的分类、目的、接收方和审批证据。它也让决策可解释，并支持暂停/恢复，而不是从自然语言中重新猜测上下文。

## Q5. 为什么需要 object-scoped state？

同一轨迹可以同时包含原始个人记录和由它派生的安全聚合。单一的“含 PII”全局标志要么会误阻断聚合，要么会放松对原始来源的保护。对象级状态分别保留分类与义务，血缘则记录两者关系。

## Q6. Data Lineage 有什么作用？

血缘回答数据从哪里来、经历了什么转换、哪个对象到达了数据汇。GDPR 演示记录了“原始记录 → 聚合计数 → 外部接收方”。它支持最小化检查和审计解释，也不会假装转换一个对象会改变源对象分类。

## Q7. 为什么需要 Capability Broker？

如果 Agent 代码仍持有原始后端或能调用未包装辅助函数，进程内 Guard 就可能被绕过。Broker 改变了能力归属：Agent 正常情况下只有类型化客户端，邮件、记忆和响应后端位于独立进程。它缩小了正常能力面，但不是 OS 沙箱。

## Q8. 为什么 Adapter 不够？

LangGraph Adapter 很适合生命周期规范化和常规框架集成，但自身无法建立完整中介。它的保证依赖调用经过包装工具，而同一进程仍可能存在原始 Python 引用。Broker 在内部复用 Adapter，并在 Broker 持有的副作用前增加持久化授权边界。

## Q9. Agent 还能绕过 Broker 吗？

如果部署向 Agent 提供其他网络、文件、子进程、插件、回调或原始后端通道，就仍可能绕过。AgentShield 的声明只覆盖经参考 Broker 路由的能力和正常 Brokered Agent 表面。生产部署还必须实施最小权限、认证 IPC、OS/容器控制并移除替代权限。

## Q10. 为什么 Repair 必须重新校验？

修复会创建不同的动作，通常也会创建不同的数据对象。若默认转换结果安全，修复代码就会成为隐式策略绕过。AgentShield 阻断不安全父事务，创建带关联关系和生效参数的子事务，并在执行前校验子事务。

## Q11. 为什么 Approval 不能直接执行？

审批只是针对特定对象、目的、接收方和操作的证据，不是通用 Allow Token。事务暂停期间，状态或参数可能变化，其他策略要求也可能仍未满足。AgentShield 记录审批，让事务返回 `CHECKING`，重启后重建状态，只有策略通过才执行。

## Q12. `effect_id` 解决什么问题？

Agent 框架会在超时、Worker 故障或 Broker 重启后重试，从而可能重复真实副作用。稳定的 `effect_id` 使 AgentShield 能识别已经提交的受支持副作用，并返回已保存的安全元数据。幂等记录保存在 SQLite 中，因此不会随进程退出丢失。

## Q13. 这是 exactly-once 吗？

不是。它是针对单个 SQLite 存储中已完成副作用的应用层至多一次重放。若 Broker 在服务商已执行但本地尚未提交时崩溃，结果无法确定，因此遗留 `EXECUTING` 事务会进入 `REQUIRE_HUMAN_REVIEW`，而不会自动重试。

## Q14. GDPR/PIPL 如何转成规则？

项目使用人工审查的 YAML 包，包含元数据、规范化要求、确定性谓词、干预、测试和官方来源链接。运行时加载所选法规包并编译有效策略集，再按受影响事实和生命周期事件建立索引。它是可审查的工程解释，不是自动法律解析或完整法条编码。

## Q15. 是否能保证 GDPR 或 PIPL 合规？

不能。项目只实现部分可在运行时执行的技术控制，用于辅助更完整的合规体系。法律适用性、有效同意、组织流程、数据主体权利、合同及大量司法辖区义务仍需要人工和组织治理。

## Q16. Detector 误报或漏报怎么办？

检测器是证据提供者，不是法律权威。参考规则对高风险未知事实选择关闭执行或要求审批，带来源的审计让输入和决策可检查。生产化应加入校准检测器、置信度策略、领域评测、受治理的人工覆盖和漂移监控。

## Q17. 实测开销来自哪里？

最新 100 次本地基准测得 Broker 路径平均 14.5311 ms，平均新增延迟 14.5289 ms。已插桩组件平均值为：策略校验 0.3933 ms、SQLite 事务持久化 1.6052 ms、幂等查询 0.1558 ms、审计持久化 0.7490 ms。其余包括回环 HTTP/进程调度和 Gateway/副作用持久化；这是确定性 Mock 结果，不是生产延迟声明。

## Q18. 如果投入生产，下一步是什么？

首先增加认证与授权 IPC、主体级能力授权、加密及可迁移存储、秘密管理和结构化运行恢复。随后接入服务商幂等键、并发租约或栅栏、防篡改远程审计和部署级沙箱。扩展法规前还需要负载、故障注入、检测器质量和策略变更评估。

## Q19. 为什么不直接让 LLM 判断合规？

LLM 可以帮助解释上下文，但随机模型不应独自控制不可逆副作用的授权边界。AgentShield 把最终决策放在显式谓词、可追溯规则、持久状态转换和可回归测试的 Gateway 不变量中。学习型分类器可以作为证据插件，而无需悄然拥有执行权限。

## Q20. 项目最大的安全假设是什么？

完整中介依赖部署确保 Agent 没有 Broker 之外的替代权限。Broker 主机、策略包、能力注册表、SQLite 完整性和审批者身份也被信任。如果任意 Agent 代码拥有主机权限或能直连原始服务，仅靠进程隔离无法保护副作用。

## 建议现场演示顺序

先运行 `agentshield demo gdpr` 并打开 Dashboard，把修复决策与原始/派生对象关联起来。再展示 PIPL 暂停、审批、重新校验，以及重启幂等结果。最后用 Gateway 不变量、威胁模型边界和最新测试/性能证据收尾，不再增加额外功能声明。
