# Adapter 与 Capability Broker 安全模型

[English](adapter_security.md)

## Brokered 安全边界

LangGraph Adapter 仍然是可信 Broker 内部负责生命周期映射的安全关键组件，但它不是唯一边界。Brokered Agent 获得的 `BrokerClient` 只有 `endpoint` 与 `timeout`；原始邮件/记忆实现和 `EffectGateway` 在独立进程中构造。

这消除了求职演示中最重要的正常 API 绕过：Agent 不再能同时持有原始后端，并绕过包装直接调用。但这并不意味着任意本地 Python 代码已经安全。

## 受保护的 Brokered 路径

- 数据源执行前的已注册 `customer.read` 请求；
- 外部 Mock 投递前的 `email.send`；
- 持久化前的 `memory.write`；
- 返回值前的 `response.release`；
- 通过新的重新校验子事务执行的修复调用；
- 通过限定证据与重新校验执行的审批调用；
- 通过持久化 `effect_id` 重放的成功重试；
- 不自动重复执行的崩溃不确定性恢复。

网关会独立加载持久状态，仅当事务为 `EXECUTING` 且能力匹配时才接受调用。因此策略授权不再只是 Agent 代码传递的进程内布尔值。

## 仍然存在的绕过路径

完整中介声明只适用于所有相关副作用均经过 Broker 的情况。范围外的绕过包括：

1. Agent 还获得其他网络、Shell、文件系统、数据库、插件、回调或记忆能力。
2. 可信 Broker 后端隐藏了未由注册能力表示的嵌套副作用。
3. 恶意代码取得本机回环端点并提交请求；参考服务没有调用方认证。
4. 某个主体修改 Broker 代码、法规包、风险/治理元数据或 SQLite 数据库。
5. 某个主体在 Broker 进程内导入或构造后端对象，或攻陷该进程。
6. 真实服务商已经执行副作用，但 Broker 在记录前崩溃，留下 `REQUIRE_HUMAN_REVIEW` 事务。
7. 多个 Broker 共享状态，但没有租约、栅栏或服务商幂等协调。
8. 使用未包装的进程内 Agent，而不是 Brokered 参考 Agent。

Python 名称私有化（`__email_backend`）只是封装手段，不是对抗性安全边界。真正的能力缩减来自进程分离，以及 Agent 不持有后端引用或凭据。

## 保留的 Adapter 不变量

在 Broker 内部，`LangGraphAdapter` 继续提供：

- 生命周期规范化与显式工具风险元数据；
- 工具结果接收前的允许调用关联；
- 对象级检测与数据血缘；
- 修复参数注入与重新校验；
- 记忆写入前与响应发布前检查；
- 错误及因果审计记录；
- 按轨迹隔离的合规会话。

Broker 集成新增两个可信操作：重启后恢复引用对象，以及记录限定范围审批/同意证据。这些能力不会作为任意策略事实注入接口暴露给 `BrokerClient`。

## 重试、修复与审批

普通重试是新的请求提案，但在创建新副作用前会查询稳定 `effect_id`。被阻断事务没有成功 effect 记录，因此会重新评估；已完成副作用则直接重放。

修复不会把不安全记录原地修改为允许。被阻断父事务保留原始决策，新子事务保存最小化后的生效参数，并在校验后执行。

审批范围由暂停事务派生，且必须完全相等。接受决定会生成生命周期证据并回到 `CHECKING`，不会直接调用网关。

## 审计与敏感状态

SQLite 审计事件将载荷型字段替换为 SHA-256 指纹与字节数。`transactions show` 对参数和嵌套结果载荷应用相同规则。

事务表本身会为持久恢复保留原始和生效参数，因此拥有数据库读取权限的主体可能访问敏感信息。运行时假设文件系统权限严格；加密、数据库授权、保留期删除和密钥管理仍属于生产工作。

## Adapter-only 模式

`AgentShield.wrap()` 支持进程内集成，并保留相应限制：绕开注册网关的直接调用依然可能发生。它适合兼容和观测，但 Brokered 路径是更强的副作用中介参考架构。
